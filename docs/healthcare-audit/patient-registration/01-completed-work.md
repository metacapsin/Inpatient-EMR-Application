# Patient Registration: Completed Work

Date: 2026-11-13. Phase 1, module 9 (roadmap item 1.5). Full scope approved and implemented — three list-filter bug fixes, server-required fields for standard registration, USCDI v3 demographics (coded, with FHIR US Core extensions), next-of-kin/legal-guardian designation, an unknown/unidentified-patient registration path, and registration-time consent. No external blocker.

## Summary for stakeholders

Three patient-list filter bugs are fixed: selecting the 19–35 age range used to silently reset to "All ages"; "Today"/"This Month" were sent to the server but never actually filtered anything; and the name column couldn't be sorted at all (it had no working sort). Registration now enforces date of birth and sex server-side for a normal registration — previously the API accepted a bare first/last name from any caller, relying entirely on the registration form's own client-side checks. Six new USCDI v3 demographic fields are captured, all using standard coded value sets (not free text) so they can round-trip through the FHIR Patient record the same way other systems expect: sex at birth, gender identity, sexual orientation, race (now multi-select, matching the federal standard that a person may select more than one), ethnicity, interpreter-needed, and communication preference. An emergency contact can now be flagged as a next-of-kin, legal guardian, power of attorney, or healthcare proxy — a real legal role, distinct from the existing free-text "relationship" field. A genuinely new workflow handles unidentified patients (trauma, unresponsive arrival): registration no longer requires a name, and a placeholder identity is generated so care isn't blocked on paperwork; the record is flagged until someone updates it with the real name. And a consent (general treatment, HIPAA Notice of Privacy Practices) can now be recorded at the moment of registration — previously impossible, because every consent record required an encounter that doesn't exist yet at registration time.

## What changed

| # | Item | Result |
|---|---|---|
| 1 | List filter bugs (BUG-06) | `'19-35'` added to the frontend's allowed age-range values (was silently coerced to "all"); backend now actually filters on `recentlyCreated=today`/`thismonth` (previously only `last5recent` had any effect); the Patient column is sortable again and genuinely sorts by name (`fullName`), not creation date |
| 2 | Server-required fields | New `createPatientBody` schema: `dOB` and `sex` are required for `registrationType: 'standard'` (the default) — enforced server-side, not just by the registration form. Deliberately **not** requiring a contact method, to avoid breaking every other internal caller that creates a patient without one for no real safety benefit |
| 3 | USCDI v3 demographics | New `patients` columns: `gender_identity`, `sex_at_birth`, `sexual_orientation`, `interpreter_needed`, `communication_preference[]`; `race` converted from a single free-text column to `TEXT[]` (multi-select, matching OMB/US Core). All coded via new `lib/uscdiCodes.js` (CDC Race & Ethnicity, HL7 Birth Sex, SNOMED CT SOGI value sets) |
| 4 | FHIR US Core extensions | `lib/fhir/patient.js` now emits `us-core-race`, `us-core-ethnicity`, `us-core-birthsex`, and `us-core-genderIdentity` extensions on `GET /fhir/Patient`. Sexual orientation, interpreter-needed, and communication preference are captured and persisted but deliberately **not** forced into a non-standard Patient extension — real US Core models sexual orientation as an Observation, and the other two have no standard Patient-level representation |
| 5 | Next-of-kin / legal guardian | `patient_emergency_contacts` gains `is_guardian` and `legal_role` (`next_of_kin`/`legal_guardian`/`power_of_attorney`/`healthcare_proxy`) — distinct from the existing free-text `relationship` label |
| 6 | Unknown-patient path | `registrationType: 'unknown'` on create: name becomes optional, server generates a placeholder (`"Unknown"` / `"Patient-XXXX"`), and `is_unknown_patient` is set — never client-settable directly, only ever derived from `registrationType`. Surfaced in the Quick Add modal as an "Unidentified patient" toggle |
| 7 | Registration-time consent | `consents.encounter_id` is now nullable; `POST /api/Consent/create` accepts a request with no `encounterId` (validates the patient exists instead of validating an encounter); new `GET /api/Consent/patient/:patientId` lists a patient's consents regardless of encounter, since the per-encounter list can't surface one with no encounter. Registration form gained two consent checkboxes (General Treatment, HIPAA NPP) that fire this on successful create |
| 8 | `deceased`/`deceasedAt` exposure | Already-existing columns (added by the admission/discharge module) are now exposed on every patient read endpoint. Deliberately **not** made writable via registration/update — that would create a second, unguarded way to mark a patient deceased alongside the existing physician-gated death-record workflow, which requires a pronouncing-physician attestation this would bypass |
| 9 | Tests | New `backend/tests/patientRegistration.test.js` (4 tests: required-fields/unknown-patient, registration-time consent, BUG-06 backend filters, FHIR extension unit tests); `tests/api.test.js`/`tests/rbac.test.js` updated for the new required fields and coded race/ethnicity; full backend suite: **123/123** |
