# Authentication / Session Hardening: Completed Work

Date: 2026-11-12. Phase 1, module 2. Approved scope implemented in full (opt-in MFA, as scoped in the proposal); no external blocker.

## Summary for stakeholders

Staff sign-in now locks an account for 15 minutes after 5 wrong passwords, enforces a NIST 800-63B-style password policy (length + a common-password check, no forced composition rules), and supports opt-in two-factor authentication (TOTP, with one-time backup codes) — nobody is required to turn it on. Deactivating a user, changing their role, or resetting their password now takes effect on that user's very next request, not whenever their current token happens to expire. "Sign out" actually revokes the session server-side now (it never did before), and a new "sign out of all devices" action exists. The refresh token moved out of `localStorage` into an `httpOnly` cookie the page's own JavaScript can't read; the access token itself is memory-only and is silently restored from that cookie on each page load. Staff forgot-password now actually emails a reset link (it silently did nothing in production before). Four places that leaked a dev-only token outside local development are now gated on an explicit flag instead of guessing from `NODE_ENV`. The platform/SMART JWT secrets can no longer silently derive from the staff one in production. An unused header that echoed the current page's URL (often containing a patient id) on every request is gone.

## Two real bugs found and fixed while implementing this

1. **The login route's generic per-request audit logger ran as a blanket `platformAdminRouter.use(...)` in an earlier module** — not from this one, but the same router-middleware gotcha nearly recurred here: removing `refreshTok &&` from `shouldBypassRefreshForUrl`'s guard (since a stored refresh token can no longer be checked for) meant *any* request to a public-but-unlisted auth endpoint (`/auth/reset-password`, `/auth/register`) would trigger a doomed silent-refresh attempt and get killed with "Session expired" before ever reaching the server. `SetPasswordPage.tsx` — the real, live password-reset page — would have broken silently. Fixed by adding the missing paths to the bypass list.
2. **The lockout counter and the "sign out of all devices" revocation initially raced with a stale dev server.** Unrelated to the code itself: this environment's `node --watch` stopped detecting file changes partway through the session, so the shared dev server on port 4000 served stale code for a while. Caught by testing against an isolated preview (the `backend-bedmgmt` / `frontend-bedmgmt` pair on 4100/5273 from `.claude/launch.json`) instead of trusting the shared one, then restarting the shared server once the stale state was confirmed.

## Verification

Full backend suite 65/65 (`npm test`), backend `tsc` clean, frontend `tsc` clean, `vite build` clean. Live-verified in the browser on the isolated preview pair: login (no MFA) → dashboard → full page reload preserves the session via the httpOnly cookie (`document.cookie` confirmed empty — the cookie is genuinely inaccessible to JS) → MFA enrollment end-to-end (secret, confirm with a real TOTP code, backup codes shown) → login now requires the second factor (confirmed via direct API call with a computed TOTP code) → MFA disabled again to leave the shared seed admin account (`admin@example.com`) in its original state. CORS preflight confirmed `Access-Control-Allow-Credentials: true` and no `X-Client-Route` in `Access-Control-Allow-Headers`.
